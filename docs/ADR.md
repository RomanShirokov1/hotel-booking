# Архитектурные решения

## ADR-001. Отдельная БД у каждого бизнес-сервиса

Booking хранит пользователей и брони. Hotel хранит номера и календарь их занятости в `room_reservations`. Hotel проверяет пересечения дат в своей БД, поэтому проверка и резервирование выполняются одной транзакцией. Обе базы H2 работают в памяти. [Схема данных](DATABASE.md)

## ADR-002. Компенсация при сбое бронирования

Booking записывает `PENDING`, вызывает Hotel по HTTP и сохраняет `CONFIRMED` после успеха. При ошибке Booking одной транзакцией записывает `CANCELLED` и задачу освобождения. Задача нужна и при тайм-ауте, поскольку Hotel мог сохранить резерв до потери ответа. Hotel хранит отметку `RELEASED`, чтобы запоздавший повтор не занял освобождённый номер.

## ADR-003. Повторы и параллельные запросы

Уникальный ключ `(user_id, request_id)` защищает от дубликатов брони. Hotel блокирует строку номера, проверяет даты и меняет счётчик в той же транзакции. Booking выполняет автоматический подбор для одного отеля по очереди, чтобы следующий запрос видел обновлённые счётчики. Такая очередь рассчитана на один экземпляр Booking.

## ADR-004. Доступ к внутренним операциям

Booking подписывает JWT закрытым ключом. Hotel и Gateway проверяют подпись открытым ключом. Подтверждение и освобождение номера принимают служебный токен с отдельной аудиторией `hotel-internal` и разрешением `room:reserve`. Gateway закрывает оба внутренних маршрута.
