# Архитектурные решения

## ADR-001. Владение данными и журнал резервирования

Booking владеет пользователями и состоянием брони. Hotel владеет номерами и занятостью ресурсов. Прямого чтения чужой БД нет. Дополнительная таблица `room_reservations` необходима: перечисленных в ТЗ `available` и `times_booked` недостаточно для проверки диапазонов дат. Это локальная проекция резервирования, а не общая JPA-сущность бронирования.

Gateway и Eureka не имеют бизнес-данных и БД. Требование H2 применяется к двум приложениям с данными. H2 in-memory выбрана по ТЗ; потеря процесса означает потерю состояния. Поэтому сценарий восстановления проверяет временные сбои связи при живых БД.

Демонстрационная конфигурация запускает по одному экземпляру каждого приложения. Для нескольких реплик Hotel или Booking потребуются общее постоянное хранилище соответствующего сервиса и координация фоновых обработчиков.

## ADR-002. Оркестрируемая сага вместо распределённой транзакции

Booking сохраняет PENDING, выполняет HTTP вне транзакции, затем сохраняет CONFIRMED либо CANCELLED. Отмена и задачи release записываются атомарно. Транзакционные операции вынесены в `BookingStore`, чтобы вызовы проходили через Spring proxy. Успешное резервирование в Hotel удерживается до отмены; автоматического TTL, способного освободить подтверждённую бронь, нет.

Если ответ потерян, фактический результат неизвестен. Поэтому отмена планирует release для всех сохранённых попыток. Worker повторяет освобождение до успеха с backoff. Из CANCELLED нельзя вернуться в CONFIRMED. Удаление зависимых данных запрещено, чтобы не потерять историю и задачи.

## ADR-003. Идемпотентность и запоздавшие сообщения

В Booking уникальна пара `(user_id, request_id)`, хранится SHA-256 нормализованных значимых полей. Игнорируемый при autoSelect roomId не меняет отпечаток. Одновременные повторы упираются в ограничение БД; проигравший читает уже созданную бронь.

Hotel сохраняет результат операции по UUID. Проверяется соответствие номеру, bookingId и датам. Отказ в резервировании также сохраняется. Release не удаляет запись, а оставляет RELEASED. Это запрещает поздний confirm даже тогда, когда release обработан первым. Хранение результатов не ограничено TTL в пределах жизни учебной БД.

## ADR-004. Блокировки и алгоритм подбора

Изменение занятости сериализуется блокировкой строки номера `PESSIMISTIC_WRITE`. Проверка отсутствия пересечений, сохранение операции и изменение счётчика находятся внутри этой транзакции. Поэтому нельзя получить две активные пересекающиеся брони на один номер. JVM-lock не используется: блокировка принадлежит БД.

Рекомендации — снимок, который может устареть. Booking выбирает минимум `(times_booked, id)` и при достоверном конфликте обновляет рекомендации. Число кандидатов ограничено тремя. В согласованной конфигурации с одним экземпляром Booking автоматические выборы по отелю сериализуются справедливыми ReentrantLock в фиксированных 64 полосах. Ожидание включено в бюджет запроса, произвольные hotelId не увеличивают память координатора. Транзакция БД во время HTTP не удерживается. Координатор обеспечивает баланс параллельных автоматических запросов на разные даты; блокировка строки номера в Hotel независимо защищает от пересечений всех бронирований. Для нескольких реплик Booking потребуется распределённая координация выбора. Глобально оптимальное распределение при произвольных ограничениях доступности не обещается.

## ADR-005. JWT, роли и внутренние операции

Используем штатный OAuth2 Resource Server без самописного фильтра проверки подписи. Booking подписывает RS256; проверяющим сервисам приватный ключ не нужен. Пользовательские и служебные токены разделены audience. Пользователь не может вызвать reserve/release даже напрямую по порту Hotel. Gateway дополнительно запрещает эти маршруты.

USER и ADMIN остаются пользовательскими ролями; INTERNAL не является доступной при регистрации ролью. Администратор наследует USER-возможности, но история всё равно фильтруется по владельцу. Токены stateless: изменение роли не отзывает уже выданный токен немедленно; срок его жизни ограничен одним часом. Полноценный отзыв токенов не входит в ТЗ.
