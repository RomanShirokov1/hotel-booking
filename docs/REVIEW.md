# Повторное ревью по ТЗ и проверка локального запуска

Проверено 1 ноября 2026 года на Windows, Temurin JDK 21.0.13.

## Результат

После исправлений полный Maven `verify` завершился успешно: **38 тестов, 0 ошибок, 0 неуспешных проверок, 0 пропусков**. Дополнительно выполнены пользовательские сценарии запуска, демонстрации и остановки на стандартных портах. Неисправленных ошибок в проверенных сценариях не обнаружено.

Ревью включало исходное ТЗ, схемы, контроллеры, JWT/роли, транзакционные границы, алгоритм резервирования, повторы HTTP, сагу, компенсации и сценарии запуска. Соответствие всем 15 критериям с указанием реализаций и проверок приведено в [CRITERIA.md](CRITERIA.md).

## Найдено и исправлено

1. **Рекомендации отсутствовали в API Booking.** Добавлены `GET /booking/recommend` и алиас `/api/bookings/recommend`, валидация и пагинация. Порядок — `timesBooked`, затем `id`. Проверены сортировка, права и реальный маршрут Gateway.
2. **404 Hotel превращался в 503; компенсация могла повторяться для отсутствующего номера.** Доменные 400/404 сохраняются и не повторяются как сетевые ошибки. Release с 404 завершает компенсацию: удалить номер с существующим резервированием Hotel запрещает. Проверены отсутствие номера до попытки и удаление между чтением и подтверждением.
3. **При ручном выборе можно было сохранить неверный hotelId.** Booking проверяет номер через Hotel и сохраняет фактический отель. Несоответствие явно переданному отелю возвращает 400 до резервирования.
4. **Проверки бюджета только перед HTTP-попыткой было недостаточно.** Тайм-аут вызова теперь ограничен оставшимся временем. Ответ после истечения бюджета не подтверждает бронь. Регрессионный тест использует ответ медленнее оставшегося бюджета, но быстрее обычного тайм-аута.
5. **Параллельный автоподбор мог использовать один устаревший снимок счётчиков.** Добавлена справедливая координация автоматических выборов по отелю в одном экземпляре Booking. Число блокировок фиксировано, ожидание ограничено бюджетом. Защита занятости остаётся в БД Hotel. Новый системный тест создаёт 12 параллельных автоматических броней на разные даты: все подтверждены, разница итоговых счётчиков не превышает единицы.
6. **Доказательства корреляции были неполными.** Идентификаторы и состояния добавлены в структурные поля логов; MDC сохранён для саги и recovery. Системный тест проверяет один traceId и bookingId в логах Booking и Hotel.
7. **Готовность приложений не гарантировала готовность маршрутов.** start.ps1 ожидает обе OpenAPI-спецификации через Gateway. stop.ps1 ожидает завершения записанных процессов. После остановки проверено освобождение всех четырёх портов.

## Границы вывода

- H2 in-memory уничтожает данные при остановке. Проверено восстановление после временного сетевого сбоя при живых БД.
- Конфигурация рассчитана на один экземпляр каждого приложения. Реплики потребуют общих постоянных БД соответствующих сервисов и распределённой координации.
- Неоднозначность ТЗ о занятости разрешена локальным журналом резервирования Hotel. H2 используется в двух сервисах с бизнес-данными; Gateway и Eureka не хранят предметные данные. Решения зафиксированы в ADR и согласованном плане.
- Проверен локальный Windows. GitHub Actions настроен, но реальный запуск CI в GitHub, размещение репозитория и отправка ссылки через форму ещё не выполнены.
- Проверки подтверждают перечисленные сценарии и нагрузку, а не отсутствие всех возможных дефектов. Баллы выставляет ментор; оценка 50/50 не гарантируется.
